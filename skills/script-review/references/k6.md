# k6 script review

Verify details against the k6 version in use.

## What to look for

- **Checks without consequence.** `check()` records failures but does not stop anything. Confirm thresholds fail the run on a bad check rate (for example `checks: ['rate>0.99']`).
- **No thresholds.** A script without thresholds can never fail in CI (see `ci-performance-gates`).
- **Init versus default function.** `open()` and imports belong in the init context. Work done there runs once per VU, so large data should use `SharedArray`.
- **Unsafe parsing.** `res.json()` on a non-JSON error response throws. Check `res.status` first.
- **Missing think time.** No `sleep()`, or a fixed one for every step.
- **Executor choice.** Closed model executors (`constant-vus`, `ramping-vus`) slow down when the system slows. Use arrival-rate executors for open-model workloads, and check `preAllocatedVUs` and `maxVUs`, since `dropped_iterations` means the target rate was not reached.
- **Tag cardinality.** Dynamic URLs without a `name` tag create one metric series per URL, bloating results and slowing the run.
- **Hot-path cost.** `console.log` per request, heavy parsing, or large string building inside the default function.
- **Response bodies.** Bodies kept when not needed. Consider `discardResponseBodies` when the script does not read them.
- **Shared mutable state.** Module-level variables shared across VUs, or assumed to be per VU.
- **Hard-coded values.** Base URL, credentials, and tokens in the script instead of `__ENV`.
- **Graceful stop.** `gracefulStop` and `gracefulRamp` settings that cut iterations off or inflate the end of the run.
- **Groups and tags.** Transactions named consistently so thresholds can target them.
