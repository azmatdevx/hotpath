# k6: authoring structure

Verify APIs against the k6 version in use.

## Suggested structure
```js
import http from 'k6/http';
import { group, check, sleep } from 'k6';
import { Trend } from 'k6/metrics';

const checkoutTime = new Trend('checkout_duration', true);

export const options = {
  scenarios: {
    checkout: {
      executor: 'constant-arrival-rate',
      rate: Number(__ENV.RATE || 5), timeUnit: '1s',
      duration: __ENV.DURATION || '10m',
      preAllocatedVUs: 50, maxVUs: 200,
    },
  },
};

const BASE = __ENV.BASE_URL;

export default function () {
  group('01_login', () => { /* requests, checks */ });
  sleep(Math.random() * 3 + 1);
  group('02_checkout', () => {
    const t0 = Date.now();
    /* requests, checks */
    checkoutTime.add(Date.now() - t0);
  });
}
```

## Notes
- Use `group()` for steps, or tags and custom `Trend` metrics when you need per-step durations in thresholds.
- Read configuration from `__ENV`. Keep the workload in `options.scenarios`, separate from journey code.
- Use `http.batch()` to model parallel requests a browser would make.
- Split shared helpers into modules and `import` them.
- Add per-request tags (`tags: { name: '/item/:id' }`) so URLs with IDs aggregate in results.
- For HAR input, a converter such as `har-to-k6` can produce a starting script. Clean and correlate it before use.
- Size `preAllocatedVUs` and `maxVUs` for arrival rate × iteration duration (including think time), with margin. For example 80 iterations per second with a 5 s iteration needs about 400 VUs. If `dropped_iterations` is non-zero, the offered load was below target.
